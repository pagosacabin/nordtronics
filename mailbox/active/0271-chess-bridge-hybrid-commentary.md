# 0271 — Chess bridge v2: Stockfish hybrid + move commentary

## Context

Task 0268 builds the DeepSeek chess-move bridge: the page POSTs
`{"fen", "moves"}`, the bridge asks DeepSeek for one move from the
legal list, validates it with python-chess, retries with the error,
and falls back server-side to Stockfish. This task is the v2 on top
of it: make the opponent strong *and* able to explain itself.

Two pieces, in order:
1. Commentary/coaching first: the bridge explains its move in plain
   words — and, when Stephen's last move was a mistake, says why it
   was bad. This is the feature a plain engine can never give, and
   Stephen's own words are that chess is not his strong point.
2. Hybrid strength underneath: Stockfish generates the top 3–5
   candidate moves with evaluations, and the model picks among them
   by personality/difficulty ("aggressive", "teach me"). Strong play
   keeps the tactics sound; the model adds the character.

Depends on 0268: build on the bridge it delivers (same service, same
Serve URL shape). If 0268 has not staged yet, wait for it — do not
rebuild the bridge from scratch.

## Task

1. Route the build to Newton via Herdr (pure software; bench firmware
   stays with Hermes). Extend the 0268 bridge in place (same service,
   same repo path in cabin-play) — do not start a second service.
2. Hybrid move-picking: on each AI turn, Stockfish (installed under
   0268) generates the top 3–5 candidate moves with evaluations.
   Send the model the FEN, the moves so far, and the candidate list
   with their evaluations, and ask it to pick one — by the
   personality/difficulty for the game ("aggressive", "teach me", or
   the default). The picked move must be one of the candidates;
   validate it with python-chess as in 0268. If the model picks
   outside the list or fails after retries, play Stockfish's best
   candidate.
3. Commentary: the bridge returns JSON `{"move": "<uci>",
   "comment": "<plain-words explanation>"}`. The comment explains
   the picked move in one or two short sentences, and — when
   Stephen's previous move lost material or walked into a tactic —
   says plainly what was wrong with it and what was better. Keep it
   short, plain, and human; no jargon, no lectures. The comment is
   generated by the same single model call as the pick where
   possible (one completion per turn, not two).
4. Difficulty: a difficulty setting for the game — fewer candidates
   and shallower Stockfish for easier, more candidates and deeper
   Stockfish for harder. Name the levels (at least easy / normal /
   hard) and how each maps to candidate count and Stockfish depth.
   The difficulty travels with the request if the page sends it, or
   defaults to normal — Newton picks the mechanism and records it.
   (The page does not send a difficulty yet; that is Juno's
   follow-up, not this task.)
5. Keep the whole round trip inside the page's 6-second budget:
   Stockfish candidate generation at shallow depth, one short model
   completion, fail fast. If the comment cannot be produced in
   budget, return the move with an empty comment — never hold the
   move hostage for the words.
6. Copilot peer review, locked lane (this is a backend API parsing
   network input): the 7-item security checklist (no hardcoded
   secrets, inputs bounds-checked, auth on every endpoint, TLS
   off-box, least privilege, fail-closed errors, pinned deps),
   pass/fail each. Fix any fail before staging.
7. Commit to cabin-play (same place as 0268). Push via SSH; gh.py
   cannot write to cabin-play.
8. Prove it: curl the Serve URL with a test position and show
   `{"move": "<uci>", "comment": "<words>"}` where the move is one
   of Stockfish's candidates, inside 6 seconds. Include one test
   where the previous move was a blunder and the comment names it.
