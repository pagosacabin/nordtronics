FINDING 1 — HIGH
server.py:445  raw body read without drain on early 400
──────────────────────────────────────────────
  raw = self.rfile.read(length)   # server.py:445

After the SLOTS semaphore is acquired and the body is read, a BadRequest raises
at parse_request() (line 446) or pick_move() raises another exception (line 447).
Both are caught by the except blocks at lines 448-455, which call _send() without
drain=True.  When a client sends a large (up to 16 384 B) POST, the entire body is
consumed before the exception path runs, so there is no drain problem for the body
itself — but if the client has pipelined a second request, or if the socket has
buffered data beyond the declared Content-Length, that trailing data is left in the
rfile buffer, and the next HTTP/1.1 keep-alive request will be misrouted.

More concretely: `self.rfile.read(length)` reads exactly `length` bytes, which is
correct; however the BadRequest path at line 448-451 does NOT set
`self.close_connection = True`, so Python's HTTP/1.1 machinery will attempt to read
a next pipelined request from the same socket.  If the attacker sent more data than
declared (the Content-Length check passes, but the socket has excess bytes because
the client lied after acquiring a slot), those bytes become the prefix of the next
request parse.  This allows request-smuggling of a second, unauthenticated request
into an already-granted worker slot.

Mitigation: add `self.close_connection = True` to the BadRequest handler at
server.py:448-451, or add `drain=True` to `_send()` calls on that path.

FINDING 2 — HIGH
server.py:433-436  Content-Length: 0 is rejected but chunked transfer is not
──────────────────────────────────────────────
  length = int(self.headers.get("Content-Length") or 0)   # line 433
  if length <= 0 or length > MAX_BODY:                     # line 436
      self._send(400, ...)
      return

The guard blocks bodies with no Content-Length by treating the missing header as 0
and refusing it.  However it does not explicitly refuse Transfer-Encoding: chunked.
Python's BaseHTTPRequestHandler does not transparently handle chunked encoding;
`self.rfile.read(length)` with a chunked body will read the raw chunk-framing bytes
rather than the decoded payload.  The JSON parser will then reject them with a
BadRequest, so the worst case is a 400, not a hang — but a client can bypass the
16 384-byte body cap by sending a small Content-Length with a chunked override.
More importantly, Python's http.server does not validate that Content-Length matches
the actual bytes received; a client can claim Content-Length: 100 and send 16 384
bytes; `rfile.read(100)` will only consume 100, leaving 16 283 in the buffer (see
Finding 1).

Mitigation: add an explicit check:
  if self.headers.get("Transfer-Encoding", "").lower() != "":
      self._send(400, {"error": "chunked bodies not accepted"}, origin, drain=True)
      return

FINDING 3 — MEDIUM
server.py:287-307  BoundedReader only limits readline(), not read()
──────────────────────────────────────────────
  def read(self, n=-1):
      return self.stream.read(n)    # server.py:304  — no byte counting

BoundedReader is designed to cap the header block: it counts bytes through
readline() and raises HeaderTooLarge, but its read() method is a plain passthrough.
This is intentional (body reads happen later and are bounded by Content-Length) but
creates a correctness hazard: if anything in BaseHTTPRequestHandler.parse_request()
calls rfile.read() instead of rfile.readline() for some versions of Python, the
header cap is silently bypassed.  Document the assumption explicitly with an
assertion or comment, or switch to a size-limited file wrapper for all reads.

Additionally, BoundedReader.__getattr__ at line 306 proxies all unknown attribute
accesses to the underlying stream, including makefile(), peek(), and other methods
used internally by http.server on some platforms — none of which go through the
readline count.  This is consistent with the existing approach but should be
documented.

FINDING 4 — MEDIUM
server.py:440-457  SLOTS.release() in finally is correct, but exception from _send()
leaks the slot only on a narrow path
──────────────────────────────────────────────
  try:
      raw = self.rfile.read(length)
      ...
  except BadRequest as exc:
      self._send(400, ...)
      return                         # <-- exits try block; finally still runs: OK
  except Exception as exc:

This is correct: Python's finally clause runs even when an inner `return` is
executed.  The slot is released in all paths.  No double-release issue exists.

However, if `_send()` itself raises an exception (e.g., a broken pipe from a client
that disconnected between reading the body and writing the response), the exception
propagates out of the except handler, back through the try/finally, releasing the
slot correctly, and then propagates to handle_one_request() where it is caught by
the standard machinery.  The journal line at lines 462-463 or 466-469 is then never
written, leaving the request unlogged.  This is LOW severity, not exploitable.

FINDING 6 — MEDIUM
server.py:151-153  CORS wildcard when ALLOWED_ORIGINS is unset sends the actual
Origin value back, not "*"
──────────────────────────────────────────────
  if not ALLOWED_ORIGINS:
      return {
          "Access-Control-Allow-Origin": origin or "*",   # server.py:153
          ...
          "Vary": "Origin",
      }

When PC_BRIDGE_ALLOWED_ORIGINS is not set (the documented default), and the request
carries an Origin header, the server echoes that exact Origin value as
Access-Control-Allow-Origin.  This is functionally equivalent to "*" for
cross-origin reads because the endpoint carries no credentials, but it is NOT
equivalent to "*" in one important way: browsers cache CORS preflight responses
keyed by (origin, path), and the Vary: Origin header is present, so each distinct
origin gets its own preflight cache entry — this is correct.  However, echoing the
exact Origin string means that if any browser or proxy miscaches the response
without the Vary header, a different origin will receive a stale ACAO header
pointing to the first origin's value and will be blocked.

More importantly, returning the caller's Origin string verbatim is a known
pattern that can enable CORS-based ambient-authority attacks IF the endpoint ever
gains cookies or session state.  It is documented as intentional for this
unauthenticated endpoint, but should be annotated with a comment warning against
adding credentials to this endpoint without revisiting the CORS logic.

No immediate exploitability. MEDIUM because the shape is dangerous.
