Security and correctness review — chess bridge commit c53c140

7-item checklist

1. PASS — No hardcoded secrets: server.py:84 reads DEEPSEEK_API_KEY only from the environment; run.sh:7-9 reads it from ~/.hermes/.env and exports it; neither file hardcodes or prints the value.
2. PASS — Input bounds: server.py:38 limits bodies to 8192 bytes and server.py:254-265 rejects missing/oversized Content-Length; server.py:34-36 caps FEN, move count, and move length; server.py:166-190 requires a JSON object, validates types and sizes, and requires a valid/legal chess position.
3. FAIL — Authentication: every POST, GET, OPTIONS, and health route is unauthenticated. server.py:231-249 serves OPTIONS and /health, and server.py:250-274 serves /chess-move and /. CORS at server.py:67-75 only controls browser origin visibility; it is not authentication. README.md:91-106 describes a tailnet-only/no-OAuth boundary, so all tailnet users can reach the endpoint and spend the DeepSeek credential.
4. PASS — TLS off-box: server.py:27-28 binds loopback and server.py:282-287 serves plain HTTP locally. README.md:91-106 says Tailscale Serve terminates HTTPS externally and forwards to 127.0.0.1:8765. That mapping is documented but explicitly not configured yet; TLS is off-box when deployed, not in this Python process.
5. PASS — Least privilege: the systemd unit at chess-bridge.service:16-31 is a user unit with no new privileges, no capabilities, read-only system/home, private tmp/devices, restricted namespaces/syscalls/address families, and resource limits. It runs as the user account rather than root, and the service bind is loopback-only.
6. PASS — Fail-closed: malformed requests return 400; unavailable or invalid model/Stockfish results end in 500 or Stockfish fallback only after model failure. Model and Stockfish moves are checked against python-chess legal moves at server.py:125-130 and 160-163. No illegal move is returned as a 200.
7. PASS — Pinned dependencies: requirements.txt:1 pins chess==1.11.2 exactly. README.md:48-52 and 98-99 documents a pinned Stockfish tarball SHA-256 and 17.1 id-name check, and server.py:57-64/296-307 probes the engine version at startup and reports/warns on it.

Numbered findings

1. HIGH — Missing application authentication / public cost abuse — server.py:231-274, README.md:91-106. POST /chess-move, POST /, GET /health, OPTIONS, and their CORS behavior have no credentials or caller identity. The tailnet boundary prevents internet reachability only after Tailscale Serve is configured, but every tailnet member can submit arbitrarily many requests and consume the single DeepSeek API key. This is especially severe because the endpoint claims to be public for the chess page and has no rate limit or quota. Authentication is not added because the task/environment forbids OAuth, but that leaves an operationally unsafe accepted risk rather than a secure control.

2. MEDIUM — HTTPS is not enforced for the DeepSeek upstream — server.py:29-30,102-109. CHESS_BRIDGE_URL is read from the environment with no scheme allowlist; an HTTP override is accepted and the Authorization bearer token is sent to that URL. Operator misuse, a compromised launcher, or a mistaken local override can expose the DeepSeek key off-box. The loopback/Tailscale controls do not protect this outbound hop.

3. MEDIUM — No upstream cost or request concurrency limit — server.py:29-36,181-210,250-274, chess-bridge.service:16-31. An unauthenticated caller can repeatedly trigger up to two model attempts plus Stockfish fallback, and ThreadingHTTPServer starts a thread per request. The 32-task and 256 MiB systemd limits bound process growth, but the service has no token bucket, per-caller quota, request semaphore, or DeepSeek budget control. Repeated tailnet calls can exhaust API spend or saturate CPU/disk. There is no CORS-enforced caller identity, and CORS cannot prevent direct or non-browser clients.

4. MEDIUM — Declared overall timeout is not enforced — server.py:32-35,181-210,250-274. HANDLER_BUDGET exists and is checked before the second model call, but there is no mechanism that ends the whole handler at 5.5 seconds. Both model calls can consume 4 seconds each, and Stockfish startup/fallback may add unbounded startup or engine overhead because STOCKFISH_TIMEOUT is never used. A slow Stockfish process or stalled upstream socket can leave handlers running beyond the README's 6-second page expectation and consume the small task pool.

5. MEDIUM — CORS configuration is permissive in the wrong direction — server.py:67-75. cors_headers() sends the nordtronics allowed origin for known origins but silently substitutes https://nordtronics.io for every unknown origin; it never rejects untrusted Origins. CORS does not authenticate or prevent server-side requests, but it is misleading and can allow a browser at a known allowed origin to receive responses for any request routing; direct HTTP clients are unaffected. This should fail closed on unknown origins rather than impersonating a trusted one.

6. LOW — Move-history entries are length/type bounded but not UCI-syntax bounded at parse time — server.py:166-190. The list accepts arbitrary strings up to 5 characters and only stockfish's push_uci may later reject one, while no replay validation is performed in parse_request/pick_move. This does not create an illegal move, but malformed history is silently advisory: stockfish_move resets to FEN on any invalid move, and model input is built with an unvalidated move list. That is inconsistent input handling and can cause nondeterministic fallback behavior for adversarial requests.

7. LOW — Unknown-origin CORS and health exposure details leak operational state — server.py:67-75,231-249. /health reveals MODEL and ENGINE_NAME to every caller and CORS sends origin-dependent headers for an endpoint with no authentication. Model and engine names are likely not secrets, but /health is unauthenticated and unnecessary for the public page. It also becomes a profiling/reconnaissance endpoint on a reachable tailnet.

8. LOW — HTTP 500 responses disclose exception-derived implementation details — server.py:269-274. The generic handler returns str(exc)[:200], including stockfish not-executable paths, runtime error text, model fallback details, and Python exception compositions. The key and prompt body are not included, but local filesystem paths and implementation state are exposed to network callers. The README promises no key/prompt logging, not no implementation disclosure; this should return a stable opaque error.

9. LOW — CORS preflight is accepted for unknown origins — server.py:231-239. OPTIONS returns 204 for any Origin, and cors_headers substitutes an allowed origin rather than a 403 or origin allowlist denial. Although the actual POST browser will not receive the matching ACAO for an unknown origin, the unnecessary preflight is accepted and can aid origin probing. Unknown origins should return 403/404 before 204.

10. LOW — README’s one-line-per-request claim is false — README.md:38-39, server.py:231-270. GET /health and OPTIONS do not call log(), and unknown POST/GET paths call log inconsistently or not at all. This is an observability/correctness defect, not a security bypass, but it makes access auditing incomplete and prevents operators from proving every request was logged.

11. LOW — Engine probe and fallback are not start-fail validation — server.py:57-64,296-307. ENGINE_NAME None or wrong causes only a startup warning, and the service continues. Model success can work, but a swapped engine does not block startup; the binary is checked by id name at startup, yet stockfish_move reopens it later and could be replaced between startup and use. Health's engine string is a snapshot, not a per-move integrity guarantee.

12. LOW — ThreadingHTTPServer lacks explicit request/header and slowloris controls — server.py:282-284. The 32-thread systemd limit and 8 KiB body cap help, but HTTP headers and header count are not bounded by application code, request read is only bounded after declared Content-Length, and ThreadingHTTPServer will accept a request stream until a header timeout not configured in this class. A tailnet peer can consume threads or time with slow incomplete requests.
